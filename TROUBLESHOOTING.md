# Troubleshooting & Monitoring

This guide is for after the plugin has been deployed and is in day-to-day use. If a
user reports "it's not working" and you don't know why, start here.

It covers all three deployment options, but most of the depth is on **Option C (full
Cowork plugin with Azure connector)** since that is the recommended, org-wide deployment
and the hardest one to observe — there is no local console or log file to tail once the
MCP server is running as an Azure Container App.

---

## Quick triage checklist

Before digging into logs, rule out the common causes in order:

1. **Is the plugin enabled?** Microsoft 365 Copilot → **Sources & Skills** (or
   **Get agents**) → confirm **D365FO Cowork** appears and is toggled on for the
   affected user.
2. **Has the user consented?** OAuthPluginVault (Option C) requires each user to
   consent once via the OAuth flow on first use. If they never saw or dismissed the
   consent prompt, every call will fail silently from their point of view.
3. **Did the client secret expire?** See [Secret expiry](#secret-expiry) below — this is
   the single most common cause of a tenant-wide outage that "used to work."
4. **Is `mcpServerUrl` correct?** Check `manifest.json` still has the real Container App
   URL (not the placeholder `d365fo-mcp.example.azurecontainerapps.io`) and matches the
   `MCP Server URL` printed by `deploy-azure.ps1`.
5. **Is the Container App actually running?** Run `deploy-azure.ps1 -TestOnly` (see
   [Step 2](README.md#step-2-deploy-to-azure)) to re-run the 4 smoke tests without
   redeploying — this confirms the server is reachable and Easy Auth is enforcing 401s.
6. **Is the metadata index stale or missing?** `index_status` reports last build time and
   object counts — an empty or very old index looks like a broken plugin but is really a
   data problem. See [Updating the metadata index](README.md#updating-the-metadata-index).
7. **Reproduce with a minimal prompt.** Ask the affected user (or reproduce yourself)
   with: `"What is the status of the D365FO metadata index?"`. This exercises
   `index_status` with no other skill logic involved, isolating connectivity/auth
   problems from skill-routing problems.

## "Authentication is still processing. Please try again."

This message is generated by Microsoft 365 Copilot's OAuth consent flow (the
`OAuthPluginVault` handshake in front of your Azure Container App), not by any code in
this repository — there is nothing to "fix" in the plugin itself, but it can be
diagnosed:

1. **Understand what the message means.** It typically appears when the OAuth
   consent/token exchange hasn't completed yet — either the user dismissed or never
   finished the consent prompt, or Copilot is waiting on a token that never arrived.
2. **Confirm the deployment option in use** (per the three options in this README and
   `manifest.json`). If this is **Option C** (Azure connector with `OAuthPluginVault`),
   the checklist below applies. If it's **Option B** (local MCP/VS Code), the cause is
   different — see [Option B — Local MCP (VS Code)](#option-b--local-mcp-vs-code).
3. **Follow the [Quick triage checklist](#quick-triage-checklist) above**, in
   particular:
   - Confirm the plugin is enabled for the user (**Sources & Skills** / **Get agents**).
   - Confirm the user actually completed the one-time OAuth consent prompt — don't just
     dismiss it, go through it fully.
   - Check whether the Azure AD app registration's client secret has expired
     (**Entra ID** → **App registrations** → **Certificates & secrets** → **Expires**
     column) — see [Secret expiry](#secret-expiry) below; this is the most common cause
     of "auth-shaped" failures that look stuck/silent.
   - Verify `manifest.json`'s `mcpServerUrl` matches the real Container App URL and
     `authorization.type` is `OAuthPluginVault`.
4. **Check [Entra ID sign-in logs](#entra-id-sign-in-logs-the-closest-thing-to-a-request-log)**
   (**Identity** → **Monitoring & health** → **Sign-in logs**, filtered to the app
   registration) for `Failure` entries with an AADSTS error code around the time of the
   failure — this shows whether the consent/token request is failing, being blocked by
   Conditional Access, or genuinely stuck.
5. **Reproduce with a minimal prompt** (e.g., `"What is the status of the D365FO
   metadata index?"`) to isolate whether this is a general auth failure vs. a
   skill-specific issue.
6. **If unresolved**, use the [Escalation checklist](#escalation-checklist) below to
   gather: deployment option, exact prompt/error text, timestamp, affected users,
   sign-in log entry, secret expiry status, and `manifest.json` settings — then
   escalate to Microsoft 365 support, Azure support, or the plugin maintainer.

## Option C — Full Cowork plugin with Azure connector (recommended, org-wide)

This is the deployment most teams run, and the one where "we don't know why it failed"
is most likely to come up, because there is no local terminal or log file on the user's
machine — everything happens inside Microsoft 365, Entra ID, and Azure.

### Where to look

| Symptom | Where to check | What to look for |
|---|---|---|
| Plugin missing from Sources & Skills | M365 Admin Centre → **Agents** → **All agents** | Plugin present, status = published, not disabled/blocked by a Copilot policy |
| "I don't have a way to connect to D365FO from here" | `manifest.json` → `authorization.type` | Must be `OAuthPluginVault`, not missing/`None` — see [README Step 6](README.md#step-6-configure-oauthpluginvault-required-for-mcp-tools-to-work) |
| Auth works for some users, not others | Entra ID → **Enterprise applications** → your app registration → **Users and groups** / **Sign-in logs** | Confirm the user's account isn't blocked by Conditional Access, MFA, or app assignment scope |
| Everyone suddenly fails at once | Entra ID → **App registrations** → your app → **Certificates & secrets** | Check the client secret **Expires** column — see [Secret expiry](#secret-expiry) |
| Unauthenticated calls return 401 (expected) but authenticated calls also return 401 | Azure Container App → **Authentication** (Easy Auth) blade | Confirm the audience/issuer configured matches the app registration used by `deploy-azure.ps1` |
| Every request fails, even a fresh consent | `az containerapp revision list` | Confirm the latest revision is `Running`; a failed or stuck revision returns errors that look identical to an auth failure — see [Container App state](#azure-side-signal) |
| Intermittent failures / timeouts | Entra ID **Sign-in logs**, filtered to the app registration | Look for `interrupted` or throttling (HTTP 429) entries around the failure time |
| Plugin responds but with the wrong data / stale skill behaviour | `manifest.json` `version` vs. what's actually installed | Confirm the tenant was updated (**Agents → All agents → D365FO Cowork → Update**) after the last skill or index change, per [Step 5 — Updating an existing deployment](README.md#step-5-install-in-cowork) |
| Correct auth, empty/stale results | `index_status` tool response | Confirm `last build time` is recent and object counts are non-zero — rebuild and redeploy per [Updating the metadata index](README.md#updating-the-metadata-index) |

### Entra ID sign-in logs (the closest thing to a "request log")

Because the Container App sits behind Azure AD Easy Auth, every ****** exchange for the
app registration created by [`deploy-azure.ps1`](README.md#step-2-deploy-to-azure) shows
up in Entra ID:

1. [entra.microsoft.com](https://entra.microsoft.com) → **Identity** → **Monitoring &
   health** → **Sign-in logs**.
2. Filter **Application** to the app registration name (e.g. `d365fo-mcp` or the
   `-AppName` value passed to `deploy-azure.ps1`).
3. Look at the **Status** column — `Failure` entries include an error code
   (e.g. `AADSTS65001` = user or admin hasn't consented, `AADSTS700016` = app not found
   in tenant, `AADSTS7000215` = invalid client secret).
4. Click a failed sign-in to see the **Conditional Access** tab — this shows if a
   Conditional Access policy blocked the request before it ever reached the Container
   App.

This is the primary signal for "auth-shaped" failures (the plugin can't connect at all,
regardless of what the user asked).

### Secret expiry

The Azure AD app registration's client secret (created by `deploy-azure.ps1`, printed at
the end of the run) has an expiry date. When it lapses, Easy Auth rejects every user's
token refresh **silently** — the plugin will appear broken tenant-wide with no obvious
error message pointing at the cause.

- Check the expiry: **Entra ID** → **App registrations** → your app →
  **Certificates & secrets** → **Expires** column.
- To recover: rotate the secret (`az ad app credential reset --id <clientId> --years 2`,
  see [Rotating the client secret](README.md#rotating-the-client-secret)), update the
  vault credential in the M365 admin registration with the new secret, and confirm the
  Container App's Easy Auth configuration still references the same app registration
  (no `manifest.json` change is needed unless the `referenceId` also changed).

### Azure-side signal

Unlike a fully managed SaaS MCP endpoint, this repo's server is a Container App you own,
so Azure gives you direct diagnostics:

- **Log stream / Application Insights** (if enabled) on the Container App shows
  request-level logs, including 401s from Easy Auth and any application errors from the
  D365FO CLI MCP server process itself.
- `az containerapp revision list --name <AppName> --resource-group <ResourceGroup>`
  confirms the current revision is `Running` and not stuck provisioning or crash-looping.
- Re-run `.\deploy-azure.ps1 ... -TestOnly` (see [Step 2](README.md#step-2-deploy-to-azure))
  to re-execute the 4 built-in smoke tests (server reachable, Easy Auth gate, Container
  App state, revision running) without redeploying — this is the fastest way to confirm
  whether the outage is on the Azure side at all.

### Microsoft 365 admin & Copilot usage reports

**M365 Admin Centre** → **Reports** → **Usage** → **Microsoft 365 Copilot** shows
adoption and activity at a tenant level (which users are actively using Copilot).
This doesn't give per-skill or per-tool detail, but it's useful to confirm a user is
actually reaching Copilot at all before assuming the plugin itself is at fault.

## Option B — Local MCP (VS Code)

This is the easiest option to debug because everything runs on the developer's own
machine with visible logs.

- **VS Code Output panel** → select **GitHub Copilot Chat** (or **MCP**, depending on
  VS Code version) from the dropdown — this shows the MCP server connection status,
  handshake errors, and tool call/response payloads.
- **Command Palette** → `MCP: List Servers` — confirms the local `d365fo-cli mcp start`
  server is registered and its current connection state.
- **Index errors**: the local server reads `d365fo-index.sqlite` directly — if it's
  missing, stale, or in the wrong location, tool calls will return errors or empty
  results that look like a connection failure. Re-run `d365fo-cli index build` and
  confirm the `D365FO_MCP_INDEX_PATH` (or equivalent) environment variable points at the
  right file.
- **Config errors**: verify `mcp.json` (`%APPDATA%\Code\User\mcp.json` or
  `.vscode/mcp.json`) points at the correct local command/executable — a typo here
  produces a connection failure that looks identical to an index or auth failure.

## Option A — Skills-only

There is no MCP server and no network call in this mode — skills only shape how
Copilot Chat/Agent phrases and routes requests, using whatever D365FO access the user's
existing tools already have. If something looks wrong here, the issue is almost always:

- The skill files weren't copied to the expected prompts folder — re-run
  `.\package.ps1` and check the copy/validation step completed.
- The behaviour the user expected actually requires a live MCP connection (Option B or
  C) — Skills-only cannot query the metadata index on its own.

## Escalation checklist

If you've worked through the above and still can't explain a failure, capture the
following before escalating (to Microsoft 365 support, Azure support, or the plugin
maintainer):

- [ ] Deployment option in use (A / B / C) and `manifest.json` `version`
- [ ] Exact user prompt and the exact response/error text received
- [ ] Timestamp (with timezone) of the failure
- [ ] Affected user(s) — one user, a subset, or everyone in the tenant
- [ ] Entra ID sign-in log entry for that timestamp/app registration, if Option C
- [ ] Whether the client secret is still valid (expiry date)
- [ ] `manifest.json` `mcpServerUrl` and `authorization.type` (never share the actual
      secret value or `referenceId` outside your organisation)
- [ ] Output of `deploy-azure.ps1 -TestOnly` and/or `index_status`, if Option C
